What DataNivra is, in plain words

Every software team needs realistic data to test with. The fastest way to get it has always been to copy the production database into a test environment. That copy now contains real customers' names, card numbers or medical records, sitting in a place that was never meant to protect them.

DataNivra is a test data management platform built the other way round. Its tagline is "Realistic test data. Production data stays home." It has two parts:

  • DataNivra Cloud (the website, the console and the API) is where people define rules, approve requests and see evidence. It only ever handles descriptions of your data: table and column names, counts, rule versions, job status and checksums.
  • The DataNivra agent is a small program you run inside your own network. It does all the work that touches actual rows: reading, masking, subsetting, generating synthetic data, checking quality and delivering the result into your test databases.
Why it matters

Your production rows are processed only by the agent inside your network. DataNivra Cloud never sees your customers' records — a breach of their cloud would not expose your data.

Before you start: what you need

  • A work email address for your own account
  • A second person or second email address you control, to act as approver (DataNivra refuses to let one account approve its own work)
  • A Windows 10 or 11 PC with administrator rights and about 10 GB free disk space
  • A GitHub account and a test repository you can change (Part I)
  • Optional: access to Amazon S3, Google BigQuery or Databricks (Part J)
  • About two working days in total — you can stop and restart at any point
About the approver account

For this evaluation it is fine to use a second mailbox you control. In real use, every person should have exactly one account; otherwise one person could approve their own requests, which breaks the protection.

D

Install the DataNivra agent on your Windows PC

~45 min

In real use the agent runs on a server inside your network, next to your databases. For this evaluation your PC plays that role. The agent is a Linux container, so on Windows you run it inside Docker Desktop using a Linux environment called WSL (Windows Subsystem for Linux).

D1Install WSL and Docker Desktop (one time)
  1. Click the Start menu, type PowerShell, right-click Windows PowerShell and choose Run as administrator.
  2. Type wsl --install -d Ubuntu and press Enter. When it finishes, restart your PC.
  3. After the restart an Ubuntu window opens and asks you to create a Linux user name and password. Choose anything you will remember — this password is only for your PC.
  4. Download Docker Desktop for Windows from docker.com and install it with the default options.
  5. Open Docker Desktop, go to Settings → Resources → WSL integration, switch on Ubuntu and click Apply & restart.
  6. Open the Ubuntu app from the Start menu. This black window is where you type every command in this guide. Type docker version and press Enter.
Expected result

docker version prints a Client and a Server section without errors. If it says it cannot connect, make sure Docker Desktop is running (look for the whale icon in the taskbar) and try again.

Pasting into the Ubuntu window

To paste, right-click inside the Ubuntu window (or press Ctrl+Shift+V). Paste one block at a time and press Enter. If a command asks for your password, type your Linux password from step 3 — nothing appears on screen while you type, which is normal.

D2Create the practice network

The agent and your practice databases will talk over a private Docker network. Create it once: 

docker network create datanivra-lab
If you see "network with name datanivra-lab already exists"

That is fine — the network already exists from a previous run. Continue to D3.

D3Create a one-time enrollment token in the console
  1. In the console, open Connect → Agents and click Install agent.
  2. Choose Docker as the install method.
  3. Enter an Agent name, for example ceo-laptop. Use exactly this name again in step D4.
  4. Click Create enrollment token (15 minutes validity is enough) and copy the token. It is shown only once. Keep this console page open: it will show the agent's heartbeat once running.
D4Start the agent

Paste the following into the Ubuntu window. The first command creates a private folder for secrets; the second asks you to paste the token; the third starts the agent. If you chose a different agent name, replace ceo-laptop in both places. 

sudo install -d -m 0700 -o 10001 -g 10001 "$HOME/datanivra-secrets"
read -rsp 'Enrollment token: ' T && echo && printf %s "$T" | sudo install -m 0600 -o 10001 -g 10001 /dev/stdin "$HOME/datanivra-secrets/enrollment-token" && unset T
docker run -d --name datanivra-agent --restart unless-stopped --network datanivra-lab \
  --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges:true \
  -e DATANIVRA_AGENT_CONTROL_PLANE_URL=https://api.datanivra.com \
  -e DATANIVRA_AGENT_AGENT_NAME=ceo-laptop \
  -e DATANIVRA_AGENT_SECRETS_DIR=/etc/datanivra/secrets \
  -e DATANIVRA_AGENT_ENROLLMENT_TOKEN_REF=file://enrollment-token \
  -v "$HOME/datanivra-secrets:/etc/datanivra/secrets:ro" \
  -v datanivra-agent-state:/var/lib/datanivra-agent \
  ghcr.io/manuelbomi/datanivra-agent@sha256:642b51b13d077cf0bb4e3d6bbb857b49d5c38712dbace6dcf2919e891d3d2be3
Important: verify the agent joined the network

After the docker run command finishes, run this check immediately. The agent must be on the same Docker network as your practice databases or it will not be able to reach them in Part E.

Run this command:

docker network inspect datanivra-lab --format '{{range .Containers}}{{.Name}} {{end}}'
Expected result

You should see datanivra-agent listed. It may also list lab-source and lab-target if you have already created them.

If datanivra-agent is NOT in the list

The agent container did not join the network automatically. Connect it manually:

docker network connect datanivra-lab datanivra-agent

Then run the inspect command again to confirm it now appears.

Expected result in the console

Within a minute, the console page shows a heartbeat and the agent appears under Connect → Agents as ACTIVE. In the Ubuntu window, docker ps lists datanivra-agent as healthy.

If something goes wrong
  • docker logs datanivra-agent shows what the agent is doing.
  • If the token expired: create a new token (D3), then run docker rm -f datanivra-agent and repeat D4.
  • The built-in health check docker exec datanivra-agent datanivra-agent doctor lists every check with PASS, WARN or FAIL.
Deploying on a Linux server? Use the quick installer

Part D walks through Docker Desktop on Windows. For a bare-metal or VM Linux host (the typical production setup), the signed quick-install script handles all the steps — Docker Compose download, system user, secrets directory, and systemd service — in one command: 

# Read the script first: https://www.datanivra.com/install.sh
curl -fsSL https://www.datanivra.com/install.sh | sudo bash

Or pin a version and pass the enrollment token non-interactively (CI, Ansible, Terraform user-data): 

sudo DN_VERSION=0.6.1 DN_ENROLLMENT_TOKEN="<token>" \
  bash <(curl -fsSL https://www.datanivra.com/install.sh)

The installer creates the datanivra system user (UID 10001), writes the token to /run/datanivra-secrets/enrollment-token (mode 0600), and registers a systemd unit that starts the agent on boot. Useful commands after installation: 

journalctl -u datanivra-agent -f   # live logs
systemctl status datanivra-agent   # service status

For Kubernetes, Helm, or cloud-provider managed infrastructure see the download packages.

Create two practice databases & connect DataNivra

~45 min

Instead of touching a company system, you will create two small PostgreSQL databases in Docker: lab-source (filled with DataNivra's synthetic sample) and lab-target (an empty database that plays the role of a QA test environment).

E1Run the setup script
  1. In the Ubuntu window type nano datanivra-lab-setup.sh and press Enter. A simple editor opens.
  2. Copy the whole script from Appendix A of this guide and paste it into the editor (right-click).
  3. Press Ctrl+O, then Enter to save, and Ctrl+X to close the editor.
  4. Run it: bash datanivra-lab-setup.sh
Expected result

The script prints five steps and ends with a table of row counts, for example commerce.orders 12, crm.customers 5. Ten tables in total. It also creates read-only and loader database accounts.

E2Give the agent the connection details

DataNivra Cloud never receives database passwords. Instead you store small connection files next to the agent and tell the console only their names. Paste this whole block at once — it sources the passwords file and then writes the connection files in a single step: 

. "$HOME/datanivra-lab/passwords.env"
printf '{"kind":"POSTGRESQL","host":"lab-source","port":5432,"dbname":"practice","user":"tdm_reader","password":"%s","sslmode":"disable"}' "$READER_PW" | sudo install -m 0600 -o 10001 -g 10001 /dev/stdin "$HOME/datanivra-secrets/lab-source.json"
for env in qa synth ci; do
  printf '{"kind":"POSTGRESQL","host":"lab-target","port":5432,"dbname":"practice","user":"tdm_loader","password":"%s","sslmode":"disable","schema":"%s_data"}' "$LOADER_PW" "$env" | sudo install -m 0600 -o 10001 -g 10001 /dev/stdin "$HOME/datanivra-secrets/lab-target-$env.json"
done
Paste the whole block at once

The first line sources the passwords file, so the lines that follow can use those passwords. If you paste each line separately, the later lines will have empty password variables and the files will be written incorrectly.

Verify the files were written correctly:

ls -la ~/datanivra-secrets/
Expected result

You should see four files: lab-source.json, lab-target-qa.json, lab-target-synth.json and lab-target-ci.json. All owned by uid 10001, permissions -rw-------.

Now run the doctor check to confirm everything is connected:

docker exec datanivra-agent datanivra-agent doctor \
  --source-ref file://lab-source.json \
  --connector POSTGRESQL \
  --target-ref file://lab-target-qa.json
Expected result

Among the checks you should see: SOURCE_REACHABLE PASS, SOURCE_READ_ONLY PASS and TARGET_REACHABLE PASS.

If you see SOURCE_REACHABLE FAIL or TARGET_REACHABLE FAIL (after the secret files are found)

This almost always means the agent container is not on the datanivra-lab Docker network, so it cannot reach the database containers by their names. Fix it with one command: 

docker network connect datanivra-lab datanivra-agent

Then run the doctor check again.

Why this happens: The agent should have joined the network when it was started (Part D4), but Docker sometimes does not apply the --network flag correctly on first run, or the agent container was recreated without that flag. Connecting it manually is the right fix.

Understanding SKIP and DEPENDENCY_FAILED in doctor output

The doctor command runs checks in sequence. If an earlier check fails, checks that depend on it are shown as SKIP or DEPENDENCY_FAILED rather than being attempted. This is expected behaviour — it tells you which check to fix first.

For example: if SOURCE_REACHABLE fails, the check SOURCE_READ_ONLY will show DEPENDENCY_FAILED because there is no point testing read-only access on a database that cannot even be reached. Fix the root-cause failure (SOURCE_REACHABLE) and re-run; the downstream checks will then run normally.

A clean output should show only PASS lines. Any WARN, FAIL, SKIP or DEPENDENCY_FAILED line means something is not ready.

E3Register the source in the console

Open Connect → Data Sources and click Add source. The registration wizard has five steps:

The 5-step registration wizard
  1. Connector type — choose PostgreSQL. Set Source name to Practice ERP, Agent to your agent name, and declare the data as Production data (DataNivra applies the strictest rules to production sources).
  2. Read-only account — the console shows the SQL commands to create a read-only database role. For this lab the setup script already created the tdm_reader role in step E1, so you can skip the SQL. If you ever register a real source, run the SQL that the console shows against that database before continuing. The commands look like this: 
    CREATE ROLE tdm_reader WITH LOGIN PASSWORD 'your-secure-password';
GRANT CONNECT ON DATABASE practice TO tdm_reader;
GRANT USAGE ON SCHEMA public, commerce, crm, hr, finance TO tdm_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA public, commerce, crm, hr, finance TO tdm_reader;
ALTER DEFAULT PRIVILEGES IN SCHEMA public, commerce, crm, hr, finance
  GRANT SELECT ON TABLES TO tdm_reader;
  3. Secret reference — enter file://lab-source.json (the connection file you wrote in E2).
  4. Validate — click Register and validate read-only access and wait for Read-only access verified. This confirms the agent can reach the database and that the account is genuinely read-only.
  5. Discovery — if prompted, review the list of fields that cross the boundary, tick I reviewed what will be sent to DataNivra Cloud, and click Run metadata-only discovery.
Discovery may run automatically

Depending on your version of the product, step 5 may happen automatically — DataNivra runs discovery as soon as read-only access is verified, without waiting for you to click. To check: open Connect → Catalog. If you see your five schemas and ten tables listed with their column details, discovery has already completed successfully. You do not need to run it again.

If you see "A source with this name already exists"

This happens if you clicked Back during registration — DataNivra already created the source before you went back. Do not try to register it again. Instead, go to Connect → Data Sources and click on the existing "Practice ERP" source. It is already registered; just continue from there.

Expected result

Under Connect → Catalog you now see five schemas and ten tables with their columns and relationships — but no actual data values, because DataNivra only received the structure.

Step 7 — Masking key reference is required

The form will not let you proceed without a masking key reference. The key ensures the same real customer always masks to the same fake name across tables, so joins still work in test data.

First, find which directory your agent actually reads secrets from — it may differ from ~/datanivra-secrets/: 

docker inspect datanivra-agent --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'

Look for the line ending in -> /etc/datanivra/secrets. The path before the arrow is your secrets directory. Common values are /home/yourusername/datanivra-secrets or /run/datanivra-secrets.

Write the masking key to that directory (replace the path with yours). The agent requires a specific keyset format — anything else causes the errors shown below: 

# Use the path shown by docker inspect above — example uses /run/datanivra-secrets
KEY=$(python3 -c "import os, base64; print(base64.urlsafe_b64encode(os.urandom(32)).decode().rstrip('='))")
printf '{"primary":1,"keys":{"1":"%s"}}' "$KEY" | sudo install -m 0600 -o 10001 -g 10001 /dev/stdin /run/datanivra-secrets/masking-key

Verify it:

docker exec datanivra-agent cat /etc/datanivra/secrets/masking-key
# Should print: {"primary":1,"keys":{"1":"base64url..."}}
Why this exact format — and what breaks if you get it wrong
  • Plain string (e.g. the hex output of openssl rand -hex 32) → SECRET_NOT_JSON_OBJECT
  • {"key": "..."} (wrong field names) → KEYSET_INVALID
  • Tink or JWK keyset JSON → KEYSET_INVALID
  • Correct format: {"primary": 1, "keys": {"1": "base64url-32-bytes"}} → success

The primary field (integer) selects which version is used when no version is specified. The keys object maps version numbers (as strings) to base64url-encoded key bytes of at least 32 bytes each. This design supports key rotation: add version 2, move primary to 2, keep version 1 for older datasets that must stay linkable.

Then type this into the Masking key reference field on the console: 

file://masking-key
All secret files must go to the same directory

Every secret file (connection files, masking key) must be written to the directory your agent actually reads from — the one shown by docker inspect. Writing to ~/datanivra-secrets/ when the agent reads from /run/datanivra-secrets/ causes SECRET_NOT_FOUND errors even though the file exists on your PC.

I3GitHub Actions: test data for every pipeline run

What this integration does — and why it matters

Many teams fall into one of two traps when testing code in CI:

  • Shared static test database — data drifts over time, parallel runs interfere with each other, and nobody knows whose change broke what.
  • Production snapshot copied into CI — real customer names, account numbers, and balances flow into GitHub runners and test logs. A data-exposure incident waiting to happen.

DataNivra's GitHub Actions integration solves both problems. Every CI run gets its own fresh, policy-governed slice of realistic test data, and production data never leaves your environment.

How the flow works (with a concrete example)

Imagine your team is building a banking mobile app. Your test suite needs 100 customer accounts with realistic balances, transactions, and linked cards — but you cannot use real accounts. Here is exactly what happens when a developer pushes code and the pipeline starts:

Step Who acts What happens
1 GitHub Actions runner The runner starts on GitHub's servers. It has no DataNivra password stored anywhere. Instead, GitHub issues it a short-lived cryptographic identity token (valid for a few minutes only) that proves "this is a run of your-org/banking-app, triggered by this commit."
2 DataNivra CLI on the runner The CLI sends that token to api.datanivra.com and says: "I am pipeline github-ci-eval. I need 100 rows of FS_EVERYDAY_BANKING data for purpose EVAL-1."
3 DataNivra cloud (policy check) DataNivra checks the ci-eval policy a human approved in advance: Is this pipeline allowed? Is 100 rows within the approved envelope? Is the purpose valid? If yes, it grants a reservation and signals your agent.
4 DataNivra agent (inside your environment) Your agent — running as a Docker container on your own server or VM — receives the instruction. It pulls masked or synthetic data (never raw production rows) and provisions exactly 100 customer accounts into lab-ci, your CI lab database. This database lives entirely inside your infrastructure.
5 GitHub Actions runner The runner connects directly to lab-ci and runs your test suite against those 100 accounts. The tests see realistic data: proper account numbers, plausible balances, linked cards — but none of it is real.
6 DataNivra CLI on the runner When tests finish (pass or fail), the CLI releases the reservation. The 100 accounts are cleared from lab-ci, making room for the next run. The release happens even if the tests fail, via if: always().
What never happens
  • Real production rows never reach the GitHub runner or its logs.
  • No DataNivra password, API key, or secret is stored in GitHub — the runner authenticates with GitHub's own ephemeral token.
  • The pipeline cannot silently take more data than approved — asking for 500 rows when the policy allows 100 returns TOTAL_EXCEEDS_ENVELOPE and provisions nothing.
  • The data does not "build up" between runs — each reservation is explicitly released, so lab-ci stays clean.
The same workflow works for any app that needs a database

The banking example above applies equally to an e-commerce order service, a healthcare records app, or an HR system. The --scenario flag selects the industry pack (e.g. FS_EVERYDAY_BANKING=100 for 100 banking customers). DataNivra provisions the right shape of data for your domain every time.

a) Find your tenant slug

datanivra org tenant

This prints your tenant slug — a short lowercase identifier like dadamoses-org. You will need it below. Do not use the UUID that appears in browser URLs.

b) Register a workload identity in the console

  1. Go to Settings → Workload Identities → Register.
  2. Name it (e.g. github-ci-eval), set the audience to datanivra:<your-slug> (e.g. datanivra:dadamoses-org), and set the trust to your GitHub repository (repo:YourOrg/your-repo:*).
  3. Copy the Workload Identity ID (a UUID).

c) Set repository variables in GitHub

In your GitHub repo: Settings → Secrets and variables → Actions → Variables → New repository variable. Create three variables:

Name Value
DATANIVRA_TENANT Your tenant slug, e.g. dadamoses-org
DATANIVRA_AUDIENCE datanivra:dadamoses-org (prefix + slug)
DATANIVRA_WORKLOAD_IDENTITY_ID The UUID from step b)
Type the values — do not paste

Pasting from certain tools can silently append a carriage-return (\r\n) to the value. That hidden character causes login to fail with USAGE: Invalid WorkloadTokenExchange: check tenant_slug. If you must paste, immediately delete to end-of-line and retype the last character.

d) Create a ci-eval policy

  1. Go to Automate → Test Data Profiles → New Profile.
  2. Name it ci-eval. Set Automatic Approval, then add the workload identity and profile settings.
  3. Have an approver go to Protect → Policies to approve it. (They will not find it under Automate — that tab only shows already-approved profiles.)

e) The workflow file

Create .github/workflows/datanivra-eval.yml in your repository:

name: datanivra-eval
on: workflow_dispatch
permissions:
  contents: read
jobs:
  test-data:
runs-on: ubuntu-24.04
permissions:
  contents: read
  id-token: write     # must be at job level, not workflow level
env:
  DATANIVRA_BASE_URL: https://api.datanivra.com
  DATANIVRA_CONFIG_DIR: /tmp/datanivra
steps:
  - uses: actions/checkout@v4
  - uses: astral-sh/setup-uv@v6
  - run: uv tool install datanivra-cli==0.3.0
  - name: Sign in as this pipeline
    run: |
      TENANT=$(printf '%s' "${{ vars.DATANIVRA_TENANT }}" | tr -d '[:space:]')
      AUDIENCE=$(printf '%s' "${{ vars.DATANIVRA_AUDIENCE }}" | tr -d '[:space:]')
      WI_ID=$(printf '%s' "${{ vars.DATANIVRA_WORKLOAD_IDENTITY_ID }}" | tr -d '[:space:]')
      datanivra login --url https://api.datanivra.com \
        --workload-identity "$WI_ID" \
        --tenant "$TENANT" \
        --audience "$AUDIENCE" \
        --make-default
  - name: Request test data within the approved profile
    id: req
    run: |
      datanivra test-data request \
        --profile-ref ci-eval@1 \
        --scenario FS_EVERYDAY_BANKING=100 \
        --purpose-ref EVAL-1 \
        -o json > req.json
      echo "id=$(python3 -c 'import json;print(json.load(open("req.json"))["id"])')" \
        >> "$GITHUB_OUTPUT"
  - name: Wait until the data is ready
    run: datanivra test-data wait "${{ steps.req.outputs.id }}" --timeout 600 --interval 10
  - name: Your tests would run here
    run: echo "Test data is ready in lab-ci"
  - name: Release the data
    if: always()
    run: |
      TENANT=$(printf '%s' "${{ vars.DATANIVRA_TENANT }}" | tr -d '[:space:]')
      AUDIENCE=$(printf '%s' "${{ vars.DATANIVRA_AUDIENCE }}" | tr -d '[:space:]')
      WI_ID=$(printf '%s' "${{ vars.DATANIVRA_WORKLOAD_IDENTITY_ID }}" | tr -d '[:space:]')
      datanivra login --url https://api.datanivra.com \
        --workload-identity "$WI_ID" \
        --tenant "$TENANT" \
        --audience "$AUDIENCE" \
        --make-default
      datanivra test-data release "${{ steps.req.outputs.id }}" \
        --reason-code TEST_RUN_FINISHED
Why id-token: write at job level

GitHub only injects the OIDC token environment variables (ACTIONS_ID_TOKEN_REQUEST_URL and ACTIONS_ID_TOKEN_REQUEST_TOKEN) when the permission is declared on the job, not just at the workflow level.

Node.js 20 deprecation warning (harmless)

You may see: "Node.js 20 is deprecated … actions/checkout@v4, astral-sh/setup-uv@v6". This is a GitHub notice about their runners, not a DataNivra issue. It does not affect the workflow and will resolve automatically when those actions release Node.js 24 versions.

Over-limit protection to test

Try asking for more than the approved limit: change =100 to =500 in the workflow. The request is DENIED with the reason TOTAL_EXCEEDS_ENVELOPE and nothing is created. This is the protection you are buying: pipelines cannot quietly take more than you approved.

After rebooting your PC

Secret files disappear after a reboot — you must restore them

On some systems the agent's secrets directory is mounted on /run/datanivra-secrets/, which is a tmpfs — a RAM-based filesystem that is wiped clean every time the PC restarts. If your docker inspect output shows /run/datanivra-secrets -> /etc/datanivra/secrets, all secret files (connection files and masking key) must be restored after every reboot.

After a reboot, do these two things in the Ubuntu window before continuing your evaluation:

  1. Restore the secret files — re-run the E2 paste block: 
    . "$HOME/datanivra-lab/passwords.env"
printf '{"kind":"POSTGRESQL","host":"lab-source","port":5432,"dbname":"practice","user":"tdm_reader","password":"%s","sslmode":"disable"}' "$READER_PW" | sudo install -m 0600 -o 10001 -g 10001 /dev/stdin "$HOME/datanivra-secrets/lab-source.json"
for env in qa synth ci; do
  printf '{"kind":"POSTGRESQL","host":"lab-target","port":5432,"dbname":"practice","user":"tdm_loader","password":"%s","sslmode":"disable","schema":"%s_data"}' "$LOADER_PW" "$env" | sudo install -m 0600 -o 10001 -g 10001 /dev/stdin "$HOME/datanivra-secrets/lab-target-$env.json"
done
    Also restore the masking key (re-run the F1 masking-key block with your stored key).
  2. Reconnect the agent to the lab network — Docker sometimes disconnects containers from custom networks on restart: 
    docker network connect datanivra-lab datanivra-agent

After these two steps, run the doctor check (E2) again to confirm everything is green before continuing.

Troubleshooting

Symptom What to do
Sign-in link says it is invalid Links work once and expire after 30 minutes. Request a new one.
"Separation of duties" when approving Expected: approve with the other account (your approver).
Agent not ACTIVE Check Docker Desktop is running; run docker logs datanivra-agent; create a new enrollment token if the old one expired.
SECRET_NOT_FOUND in doctor The connection files in ~/datanivra-secrets/ are missing. Re-run the E2 paste block.
SOURCE_REACHABLE FAIL or TARGET_REACHABLE FAIL The agent is not on the datanivra-lab network. Run docker network connect datanivra-lab datanivra-agent.
"A source with this name already exists" when registering The source was already created. Go to Connect → Data Sources and use the existing one.
CLI says the code expired Run datanivra login --url https://api.datanivra.com again and approve within 10 minutes.
USAGE: Invalid WorkloadTokenExchange: check tenant_slug in GitHub Actions The DATANIVRA_TENANT variable was pasted with a hidden \r\n appended. Delete the variable and re-enter the slug by typing it manually.
INVALID_CREDENTIALS (exit code 3) in GitHub Actions The --url flag is missing on the login command, or DATANIVRA_TENANT contains the UUID instead of the slug. Run datanivra org tenant locally to get the correct slug.
GitHub run waits and times out Your PC or Docker Desktop was off, or the agent is not ACTIVE. Start it and re-run the workflow.
Doctor shows SKIP or DEPENDENCY_FAILED A prerequisite check failed. Fix the first FAIL line you see (most often SOURCE_REACHABLE FAIL), then re-run the doctor command. Dependent checks will run once the root cause is resolved.
Secret files missing after reboot (SECRET_NOT_FOUND) Your secrets directory is on a /run/ tmpfs that clears on reboot. Re-run the E2 paste block to restore the connection files, then run docker network connect datanivra-lab datanivra-agent to reconnect the agent.
